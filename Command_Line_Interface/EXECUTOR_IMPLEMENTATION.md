# executor.py — Implementation Report

**Scope of this delivery.** The new `executor.py` (the runtime layer between the wizard's `RunPlan` and `run_benchmark()`), the confirmed satellite changes to five framework files and four CLI files, wizard back-navigation, the plugin-system connection, the per-run Q(V)/CFG parameter channel, and the verification evidence for all of it. Every signature, field name, and registry key referenced below was read from the source files, not reconstructed from the task description; where the two disagreed, the file won and the disagreement is recorded here.

---

## 1. Architecture: where executor.py sits

The CLI now has three layers with a strict downward dependency direction. `__main__.py` owns the interactive session: it calls `run_wizard()`, shows the `print_run_plan()` preview, offers the preset save, and finishes with `sys.exit(executor.execute(plan))`. `executor.py` owns everything between a confirmed `RunPlan` and a finished run: translation, resolution, validation, orchestration, publishing, and the exit code. The framework (`benchmark_runner.py` and everything below it) is untouched at runtime except through two sanctioned channels described in §6, and remains fully usable by Python-proficient students through `run_benchmark_script.py` exactly as before — nothing in the framework imports the CLI, the CLI's overrides default to the historical constants, and the direct-script path never passes through `executor.py`.

`execute(plan)` runs five phases. Phase 0 validates the configuration and applies the runtime channels (Q(V) overrides, violation limits, hardware pre-check, plugin firmware confirmation). Phase 1 resolves the network and profiles. Phase 2 builds the `BenchmarkConfig` and the live-streaming `PublishHandle`, and saves a `run_plan.json` copy into the run's output directory so every run is reproducible from its own artefacts. Phase 3 is the benchmark itself, routed through `plugin_runner.register_and_run()` when a controller plugin is attached and `run_benchmark()` otherwise. Phase 4 publishes the dashboard JSON (including a second publish pass for the HC-stressed re-benchmark when present) and prints the summary table. Each phase maps its failures to a distinct exit code, and the phase-3 catch-all is worded so a student immediately distinguishes "your plugin code crashed" from "your config was invalid" from "the hardware didn't respond".

## 2. RunPlan → BenchmarkConfig translation (Task 1)

The verified `run_benchmark` signature is `run_benchmark(net, profiles, network_id="unknown", config=None) -> BenchmarkResult` — not `run_benchmark(config)` as the task paraphrased — so `build_benchmark_config()` produces only the config while `build_net_and_profiles()` produces the other inputs.

The study mapping uses the verified `SCENARIO_REGISTRY` numbering (1 baseline, 2 OLTC, 3 SVC, 4 Volt-Var local, 5 Volt-Var coordinated, 6 OPF) with the decisions you confirmed: `scenario_comparison → [1,2,3,4,5]` with `run_hc=False` (OPF excluded — it has its own study and is unreliable outside CIGRE MV); `voltage_variation → [4,5]`; `opf_benchmark → [6]` (correcting the originally proposed `[5]`, which would have run Volt-Var coordinated); and `hosting_capacity → scenarios=[], run_hc=True` with the stressed re-benchmark opt-in through the new `plan.hc_stressed` flag, which sets `run_hc_scenarios=True`, `hc_stress_scenarios=[1,2,3,4,5]`, and supplies the profile factory that `benchmark_runner._validate_inputs` requires (the original mapping with `run_hc_scenarios=True`, no factory and an empty inherited scenario list would have either raised `ValueError` or re-benchmarked nothing).

The OPF guard fires at config-build time from the plan's network fields alone. CIGRE MV presets pass. Any SimBench network — the preset or an assembled code — is refused with a message naming the actual mechanism: `runopp()` fails because the HV/MV transformer impedance contrast produces an ill-conditioned PYPOWER admittance matrix. Other presets are refused as unvalidated, and custom/plugin networks get an explicit interactive confirmation (default No) rather than a hard block, since a researcher may legitimately have built an OPF-solvable network while a student almost certainly has not.

`v_min`/`v_max` map to `BenchmarkConfig.v_min/v_max`; `dry_run = not plan.hardware`; `port = plan.port`; `output_dir = <plan.output_dir>/<run_id>`; `write_csv=True`; `publish_fn` is the `PublishHandle` built in phase 2 with `update_every_k = plan.stream_every_k`. The remaining `ParameterConfig` fields flow through the runtime channels in §6 or are documented as inert in §8.

## 3. Network and dataset resolution (Task 2)

`build_net_and_profiles(plan) -> (net, profiles, network_id, profile_factory)` dispatches on the four network source types. A deliberate order of operations applies on every path: load the network, apply the optional modifications (DER injection and switch opening — **before** profile building, so injected sgens receive profile columns), build or accept the profiles, apply the scaling dicts to the net tables and the matching profile columns together, apply the time-window slice, then run the resolution check and focus-bus validation.

**Presets.** `network_catalogue.py` stores menu data only — the `RunPlan` docstring's `PRESET_CATALOGUE[preset_name]()` was stale — so the executor owns the `preset_name → constructor` mapping, verified against pandapower 3.4.0: `sb.get_simbench_net` for the SimBench preset, `create_cigre_network_mv(with_der=…)`, the seven standard Kerber constructors, the ten `kb_extrem_*` extreme variants, the five synthetic voltage-control LV classes, and all 18 Dickert presets expanded programmatically over `(feeders_range, linetype, customer, case)` with the API's literal values (`'average'` not `'avg'`; `'C&OHL'` for the mixed line type). A coverage test asserts every one of the 44 catalogue entries has a loader, so a future catalogue addition without a loader fails loudly in tests instead of at a student's terminal.

**SimBench codes** go straight to `sb.get_simbench_net(code)`, with the failure message noting that the wizard assembles codes from menu choices but not every combination exists in the dataset.

**Custom files** are imported with `importlib.util.spec_from_file_location` inside a full try/except cascade: missing file, wrong suffix, exception during import ("this is a bug inside your custom network file, not in the framework"), missing factory function (the message lists the callables that *do* exist in the file), non-callable attribute, and a duck-type check that the returned object actually has `bus`/`line`/`load`/`sgen` tables. No raw `ImportError`/`AttributeError` traceback reaches the student.

**Plugins** call the verified `network_plugin.load_network_from_yaml(yaml_path) -> (net, profiles)`, surface `validate_network_plugin()` warnings with an interactive proceed/cancel, take `network_id` from `plugin_meta["name"]`, and hold `make_profile_factory(yaml_path)` for the HC path. If DER placements modified a plugin network, the profiles are rebuilt through that factory so the new elements get columns — the plugin YAML's own strategy stays the single owner of profile building. The dataset step is skipped for plugin networks (the wizard prints why), and `plugin_meta`'s `v_min`/`v_max` are overridden by `ParameterConfig` per your confirmed precedence.

**Datasets.** `simbench_native` is only accepted when the network actually is SimBench (cross-field check the wizard cannot do) and calls `build_annual_profiles(net, net_name, simbench_code=code)`. `dwd` validates the directory and that at least one CSV mentioning the station ID exists anywhere under it, then calls the fallback path. `custom` uses your confirmed interpretation: `DatasetConfig.custom_path` **is the data directory** handed to `build_annual_profiles(data_dir=…, file_map=…, col_map=…)` — the only interpretation with an existing consumer, since no direct-load path exists in `profile_builder.py`. The wizard's custom-dataset prompt was reworded accordingly. On the three non-plugin paths, the HC profile factory is a closure over the same builder kwargs with `_hc_stressed` appended to the net name, so the stressed re-benchmark rebuilds profiles with the identical strategy (and the identical time-window slice).

One documentation mismatch discovered while testing: `DatasetConfig`'s comment describes a `<data_dir>/PV, /Wind, /Temperature` subdirectory layout, but `profile_builder.find_dwd_file()` globs **flat** in `data_dir` (`data_OBS_DEU_PT10M_<code>*.csv`, hyphenated `RAD-G`). The executor's directory validation uses a recursive glob so it accepts either layout, but profile building itself requires the flat layout unless a `file_map` is supplied. Worth fixing the comment (or the glob) at some point; I changed neither, since both files are yours to rule on.

## 4. Runtime validation (Task 3)

The wizard validates every field in isolation; a read of `wizard.py` confirmed it performs **no** cross-field checks. The executor therefore owns, without duplicating wizard-time validation: `v_min < v_max` plus a plausibility band `[0.5, 1.5]` pu; dataset↔network compatibility; study↔network compatibility (the OPF guard); custom-file/plugin-YAML existence before any expensive work; `focus_buses ⊆ net.bus.index` after loading; the timestep-resolution consistency check (warn-only, §8); and the hardware plumbing.

The hardware pre-check runs only when the run would actually open the port (`plan.hardware` and the scenario set intersects {4, 5}, or the HC-stressed re-benchmark is on, or a controller plugin is attached). The verified behaviour of `ArduinoSerialInterface` is that `open()` raises pyserial's raw `serial.SerialException` on a missing or locked port and `ImportError` when pyserial is absent, while handshake failures surface as `SerialConfigError` from `configure()`. The pre-check therefore confirms pyserial is importable, checks the configured port against `serial.tools.list_ports` (the failure message lists the ports that *are* present and the usual RPi device names), and probe-opens it once — costing one extra DTR reset cycle, which is harmless since scenario 4's own `open()` waits the mandatory 2 s `ARDUINO_RESET_DELAY_S` regardless. All of this fails before the annual run starts, not at the first timestep's serial timeout.

The confirmed exit-code set is `OK=0, CONFIG_ERROR=2, NETWORK_LOAD_ERROR=3, DATASET_ERROR=4, PLUGIN_ERROR=5, HARDWARE_ERROR=6, SIMULATION_ERROR=7, PUBLISH_ERROR=8, INTERRUPTED=130`, carried by a typed exception hierarchy (`ExecutorError` subclasses hold their `ExitCode` and a context string for `print_error_message()`). Two orchestration details worth knowing: a publish failure after a successful simulation returns 8 but still prints the full summary with the intact CSV path, and a run in which the framework's failure isolation caught scenario crashes (failed rows in the comparison table) returns `SIMULATION_ERROR` rather than 0, so shell scripts notice partial failures that a human would spot in the table.

## 5. The plugin connection (confirmed option (a))

`NetworkConfig` gained `source_type == "plugin"` with a `plugin_path` field, and `RunPlan` gained `controller_plugin_path`, both saved and restored through `to_dict`/`from_dict` — a plugin run's preset JSON reproduces the plugin run, which was the deciding argument for (a) over the argparse bypass. The wizard offers the network plugin as a fourth source (with a note that relative paths inside the YAML resolve against the YAML's folder and that the dataset step will be skipped) and asks one optional controller-plugin question at the end. In the executor, an attached controller plugin routes the whole run through `register_and_run(yaml, net, profiles, network_id, benchmark_config, return_benchmark=True, port=…)`, so the custom controller appears as an extra comparison row next to the study's scenarios and the returned `BenchmarkResult` feeds the normal publish path. Plugin-definition failures (bad YAML, missing module, wrong function name) are caught as `PLUGIN_ERROR` before any simulation; a crash *inside* the custom controller surfaces as the framework's `RuntimeError` and is reported as `SIMULATION_ERROR` with the message "YOUR CUSTOM CONTROLLER CRASHED inside the simulation loop … the traceback above comes from your plugin code".

## 6. Per-run Q(V) parameters: the CFG connection (route J-a, via a setter)

You confirmed route J-a — thread per-run Q(V) parameters properly rather than mutating constants before import. During implementation I found a variant that fulfils J-a's guarantee with three small diffs instead of five threading diffs, and it is delivered with that deviation **flagged for your accept/reject**: instead of adding a `qv_params` field to `BenchmarkConfig` and new parameters to `run_scenario_4` and `VoltVarController`, `volt_var_controller.py` gained a validated public setter, and the two modules that had frozen the value at import time were switched to call-time reads.

The mechanism rests on how the constants are consumed. `QVCharacteristic.compute_setpoint()` and the CFG f-string inside `ArduinoSerialInterface.configure()` both read `Q_RATIO`/`U1_PU`…`U4_PU` as module globals **at call time**, so rebinding the module attributes updates the dry-run curve and the hardware CFG message automatically. The only stale copies were the `from volt_var_controller import Q_RATIO` bindings in `scenario_4_volt_var.py` (dynamics ceiling and `q_max_arr`) and `sensitivity_coordinator.py` (`self._q_max` sizing); both now do `import volt_var_controller as _vvc` and read `_vvc.Q_RATIO` at the point of use, with a comment explaining why. The new `set_qv_parameters(q_ratio, u1..u4)` validates with exactly the firmware's `ERR:CFG_INVALID` matrix (all finite, `0 < q_ratio ≤ 1`, strictly increasing breakpoints — strict monotonicity keeps both ramp denominators positive, the same division-by-zero guard the AVR enforces) and commits parse-then-write so a bad call can never half-update the curve. `reset_qv_parameters()` restores the compile-time defaults.

The result is the §9.1 single-source-of-truth invariant preserved *by construction*: one call changes the dry-run curve, the coordinator's `q_max`, the dynamics ceiling, the saturation counter, **and** the value the Arduino receives over CFG — a Python/firmware curve mismatch cannot occur, which was the failure mode the original J-a threading was designed to prevent. This differs from the rejected J-b in the two ways that mattered: there is a validated public API instead of raw constant mutation, and there is no import-order fragility because the consumers now read at call/construction time, verified by test (framework imported first, setter called after, both `scenario_4` and the coordinator saw the new value). If you prefer the literal five-diff threading anyway, say so and I will convert; the setter’s call sites make that a contained change.

In the CLI, `ParameterConfig` gained optional `q_ratio`, `u1_pu`…`u4_pu` (None = framework defaults), the wizard asks for them behind a single opt-in confirm with the same validity checks at input time, `print_run_plan` shows them, and `executor.apply_qv_overrides()` applies them in phase 0 — printing the applied curve with an explicit note that it reaches the dry-run curve, the coordinator sizing, and the Arduino CFG message. **Caveat that blocks nothing but must be said:** the `volt_var_controller.py` and `volt_var_arduino.ino` you uploaded in this conversation are the CFG-enabled versions and all diffs were made against them, but the copies in the project knowledge folder still predate the CFG extension — make sure the repository the CLI lands in carries the CFG-enabled pair, or the CLI's Q(V) overrides will apply to the Python side only and `configure()` will not push them to the board.

## 7. Hardware controller plugins (your question 9, answered and implemented)

**What the limitation was.** A controller plugin's algorithm is a Python function executed on the RPi/laptop inside `run_custom_controller_scenario()`'s loop; `hardware: true` in the YAML raised `NotImplementedError`. So yes — your reading was right: previously a custom control algorithm could only ever run as software, and a researcher could not exercise their own algorithm through the actual serial HIL path. The Arduino only ever runs whatever firmware is flashed on it, and the stock firmware implements the VDE Q(V) curve specifically — the framework cannot "upload Python" to the board.

**What is implemented now**, following your Python-only ⇒ dry-run intuition. A hardware plugin YAML must carry a `firmware:` field naming the researcher's `.ino` sketch (resolved YAML-relative, existence-checked, `.ino`-suffix-checked by `load_plugin`); the Python `function` stays mandatory as the dry-run mirror of the same algorithm — exactly the `QVCharacteristic`↔`compute_q()` mirror pattern the stock controller uses. At run time, `register_and_run()` gained a keyword-only `port` argument and routes as follows: hardware YAML **and** a non-dry-run config **and** a port ⇒ the controller function is replaced by a `HardwareControllerFn`, a serial-backed callable that lazily opens the port on first call, performs the INIT/CFG/P handshake with the constant `p_installed_mw` the loop passes every timestep (reconfiguring automatically if it changes, e.g. in an HC re-benchmark), answers each call through `exchange_batched()`, and is closed in the same `finally` that cleans the scenario registry (sending `END` so the board resets even after a failure). Any other combination — dry run, no port, or `hardware: false` — falls back to the Python mirror with a logged warning naming the unused sketch.

**The failsafe cascade** you asked for has three layers. First, the YAML must name the sketch and the file must exist, so every hardware run is traceable to a specific firmware file. Second, the CLI asks an explicit interactive confirmation before the run: "*<sketch>* is flashed on *<port>*?" — necessary because the serial protocol can verify the message format but not the algorithm behind it (two firmwares that both ACK the handshake are indistinguishable on the wire; recommend plugin authors add a firmware-ID string to their sketch and check it manually). Third, the handshake itself: the researcher's firmware must implement `INIT`/`CFG`/`P` (ACKing CFG even if the algorithm ignores the Q(V) parameters) and answer `V:` with `Q:`; a board running anything else fails `configure()` loudly with `SerialConfigError` instead of silently mis-controlling. Automated re-flashing via `arduino-cli` was deliberately **not** included in this pass — compile-and-upload automation has its own failure surface (board FQBN detection, toolchain presence on the RPi) and deserves its own reviewed task; the confirmation prompt covers the safety requirement meanwhile.

## 8. ParameterConfig consumer audit — what now works, what remains inert

`v_min`/`v_max` were already wired through `BenchmarkConfig`. The thermal/angle limits now work through the second sanctioned channel: `detect_violations()` and `detect_violations_3ph()` had their keyword defaults changed from import-time constant copies to `None`, resolved against the **current** module constants at call time, and `executor.apply_violation_limits()` rebinds those constants per run — with your confirmed fallback semantics (an invalid value warns and keeps the framework default instead of aborting). Effect and honest scope: `LINE_MAX_LOADING`, `TRAFO_MAX_LOADING`, and `VA_DIFF_MAX_DEGREE` now govern every default-argument `detect_violations()` call — the scenario 4 HIL loop's pre/post reports and curtailment gate, the coordinator, and hosting capacity — and `V_MIN`/`V_MAX` are rebound too so those calls agree with the runners' inline checks. `UNBALANCE_MAX_PERCENT` is applied but currently reaches no result because no runner performs a three-phase power flow; that is a statement of fact, not behaviour invented to close the gap.

`der_scaling`/`load_scaling` (confirmed D1) are implemented in the executor as the natural consumer: the bus-keyed dict with the `{None: factor}` sentinel is resolved to per-element factors, applied to `net.load` (`p_mw` **and** `q_mvar`) or `net.sgen` (`p_mw` **and** `sn_mva`, so the inverter Q ceiling scales with the plant instead of silently oversizing), and to the matching profile columns — profiles are element-indexed, which is why the bus→element resolution exists. This is the exact pattern `run_benchmark_script.py` documents in its manual scaling block, now reachable without editing code. To your question — yes, the script's other two manual blocks are now in the CLI too: DER injection (`NetworkConfig.der_placements`, creating `type="PV"` sgens with the same field set as the script's block) and switch manipulation (`NetworkConfig.switches_to_open`), both asked as optional wizard questions, both applied before profile building, both index-validated against the loaded net with messages telling the student how to find valid indices.

`timestep_resolution` (confirmed D3) is a consistency check, not a control: after the profiles are built, the actual `times[1]-times[0]` is compared and a mismatch **warns** — deliberately not a 15/10-minute whitelist, so a future 1-minute weather station or hourly ERA5 source runs unimpeded, with the dynamics layer parameterised from the actual dt as it always was. And the finding required by Task 1, stated plainly: `execution_mode`, `remediation_profile`, `focus_buses` (beyond the new existence validation), and `rolling_window_n` have **zero consumers** anywhere in the runner stack; they are provenance/display fields, and the "remediation logic" the wizard's voltage_variation label promises does not exist in the framework. `stream_every_k` is the one streaming field with a real consumer and now drives `PublishHandle.update_every_k`.

## 9. Wizard back-navigation and the flagged improvement

`run_wizard()` is now an ordered step list walked by index — Study (with the HC-stressed sub-question), Execution mode, Remediation, Network, Network modifications, Dataset (auto-skipped for plugin networks), Time window, Parameters, Hardware, Controller plugin — with every menu offering "0 — go back" and every free-text prompt accepting `<` as a back token (chosen because it is not a plausible path, station ID, number, or dict literal). Either raises `BackRequested`, caught only by the step loop, which decrements the index; re-entering a step re-asks its questions with the standard defaults (carrying prior answers forward as defaults is a possible refinement, not done in this pass). All existing `_ask_*` functions and menu texts were preserved; the mechanical change was routing their raw `Prompt/IntPrompt/FloatPrompt` calls through the back-aware `_ask_value()`. Two small limitations by design: the yes/no `Confirm` prompts don't take the back token (the next real prompt does), and back inside a multi-question step returns to the *previous step*, not the previous question.

**The one improvement implemented beyond the confirmed list — accept or strip:** a Time window step (`RunPlan.time_period`/`time_index`, default full annual) that slices the built profiles through the existing `scenario_result.slice_profiles()` — the same fast-iteration mechanism `run_benchmark_script.py` uses. Rationale: without it, every CLI run is a 35k–52k-timestep annual run, which makes the wizard effectively unusable for the students it exists for, and untestable end-to-end. It is additive (default preserves full-annual research behaviour), the HC profile factory applies the same slice so the stressed re-benchmark stays comparable, and publishing uses the sliced profiles so dashboard and benchmark cover the same window. Every touched line is marked `FLAGGED IMPROVEMENT` in the source; stripping it is a contained deletion if you reject it. Two further small additives in the same spirit: `execute()` saves `run_plan.json` into the run's output directory, and `print_run_plan()` gained rows for all new fields so the pre-run confirmation is complete.
